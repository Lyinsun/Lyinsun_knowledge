# 工程知识库 Agent 指示

本仓库是可移植的工程知识库，权威内容以 Git 中的标准 Markdown 为准。开始任何工作前，先阅读 `kb.config.yaml`、`index/topic-map.md`、本文件，以及任务相关目录的 README。

## 内容归属

- 可验证的架构、接口、行为、配置语义和排障结论：写入对应主题目录。
- 设计取舍和已批准的选择：写入 `decisions/`，使用 ADR 模板。
- 原始材料的出处、检索时间、许可和可见性：写入 `sources/`。
- 未验证问题、一次性查询与后续动作：写入 `qa/`；确认后再沉淀为权威笔记。
- 不确定信息必须标记为 `status: draft` 或 `verification: pending`，不能伪装成事实。

## 查询流程

1. 从 `index/topic-map.md` 选择最相关的主题入口。
2. 使用 `rg` 搜索主题、稳定标识和来源 ID，再阅读候选笔记。
3. 区分“已验证事实”“合理推断”“待验证项”，并列出实际使用的文件。
4. 除非用户明确要求更新，否则查询只读，不改写笔记或索引。

## 写入流程

1. 先查重，并判断信息是否已有权威笔记。
2. 为外部材料创建或更新来源记录；不要把机密原文复制入仓库。
3. 从 `_templates/` 复制合适模板，填写所有必填字段和稳定 `id`。
4. 在正文中说明范围、事实、限制、来源和复审条件。
5. 新建跨笔记关系时，在两端都加入相对 Markdown 链接；来源记录的“派生笔记”必须列出使用它的权威笔记，每篇权威笔记也必须在“来源”中链接回来源记录。具体模式见 `docs/LINKING.md`。
6. 更新 `index/topic-map.md`，然后运行 `knowledge-lint` 与 `git diff --check`。

## 双向关联

- 使用普通 Markdown 相对链接，不使用依赖某个编辑器的 wikilink 语法。
- A 笔记引用 B 时，B 的“关联内容”也必须链接回 A；这才是可迁移的双向链接。
- 一篇来源记录要在“派生笔记”中列出所有使用它的权威笔记；每篇权威笔记在“来源”中链接回该来源记录。
- `index/topic-map.md` 和 `index/relationship-map.md` 是导航层，不替代笔记之间的实际互链。

## 检查的定位

- `knowledge-lint` 是给 Agent 和维护者排查遗漏的建议性工具，不自动改写内容，也不替代内容判断。
- 默认运行仅报告问题；Agent 应优先修正与当前改动相关的提示，再说明遗留缺口。
- 只有用户明确要求 CI 门禁或严格发布检查时，才使用 `--strict` 将检查结果作为阻断条件。
- `kb.config.yaml` 是人类与 Agent 共用的描述性清单。修改其中的目录或字段约定时，同步更新模板、Agent 指示和检查器基线。

## 隐私与安全

- 禁止提交个人身份信息、联系方式、真实组织与客户名称、内部地址、生产配置、凭据、令牌、私钥、会话、未脱敏日志和受限原文。
- 使用 `Example System`、`example.invalid`、`TEAM-A`、`SRC-0001` 等占位符。
- 发现疑似敏感材料时停止扩散，报告文件和风险类别；不要在回复、索引或新笔记中复述敏感值。
- 共享前遵循 `docs/PRIVACY.md`，并运行只读检查。

## 兼容性

仅使用 CommonMark/GitHub Flavored Markdown、相对链接和 YAML frontmatter。不要使用编辑器专属语法、绝对本地路径或厂商专属命令作为知识库正确运行的前提。
