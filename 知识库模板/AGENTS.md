# Knowledge Base Guidelines

## 角色定位

把本仓库当作可追溯的知识库。基于当前文档、代码、配置、测试和授权的只读查询形成结论，明确区分已验证事实、合理推断和未验证信息。

## 查询入口

- 第一个读取 `_index/topic-map.md`，再进入长期页面或专项 `README.md`。
- 索引不足时，递归搜索七个长期目录和 `initiatives/`。
- 只有需要核对原文、时间点或证据链时才读取 `raw/_manifest.md` 和对应快照。
- 文档与事实源冲突时，以当前代码、配置、数据或权威来源为准，并报告差异。

## 内容路由

- 脱离当前任务仍成立的内容进入 `architecture/`、`services/`、`modules/`、`infrastructure/`、`workflows/`、`concepts/` 或 `external/`。
- 有明确目标和结束条件的需求、调研、方案、交付和状态进入 `initiatives/<name>/`。
- 需要保留原貌的输入和证据进入 `raw/`，原则上不静默覆盖已归档快照。
- 架构正文必须位于 `architecture/<scope>/<page>.md`；`architecture/` 根目录只保留 `README.md` 和可选的 `overview.md`。
- **新老划断与渐进演进原则（增量严格，存量渐进）**：
  - **新文档 100% 严格执行**：凡是新创建的方案、架构、模块、Wiki 与快照，必须从 `_templates/` 对应模板派生并严格遵守三段式规范；
  - **存量文档不搞一刀切全量重构**：严禁为了追求外观形式整齐而批量重写、修改或搬迁历史旧文档，避免破坏历史事实源并造成海量 Git 噪点；
  - **触碰即升级（童子军原则）**：只有当某篇既有文档面临实质性重大重构、方案大版本迭代或重新成为活跃主干时，才顺带按本规范重构为三段式。优先更新已有页面，避免重复事实源。

## 页面规范

- 正式页面必须包含 `title`、`repo`、`category`、`tags`、`created` 和 `updated` frontmatter。
- `category` 只能是七个长期分类之一或 `initiatives`。
- 长期页面 `status` 可使用 `active/stale/archived`；专项页面使用 `planned/in_progress/blocked/completed/cancelled`。
- 每页 frontmatter 后的第一段是一句话摘要，供索引引用。
- 使用 lowercase kebab-case 路径、相对 Markdown 链接和精确的事实源定位；不大段复制代码或原文。
- 活动文档、Skill、模板、脚本和配置不写死个人/机器相关的绝对路径；必须使用绝对路径时通过环境变量、脚本自定位或安装时生成值解析。
- **正文必须遵循统一的“三段式”渐进展开结构（从 `_templates/` 对应模板派生，不自创不一致结构）**：
  - **第一部分：全景状态感知（Mermaid 状态图）**：必须保持全貌独立完整，人类读者仅看本图即能掌握全局边界与演进现状。统一遵循状态视觉编码：
    - `实线框 + 实线连接 (绿色)`：已上线、稳定运行或已达成共识的链路；
    - `虚线框 + 虚线连接 (黄色/橙色)`：设计中、规划中或本次专项改造推进中的链路；
    - `灰色细边框 (灰度)`：已废弃、计划下线或明确在范围外的链路；
    - `模块分区 (subgraph)`：按业务/架构层级清晰区分系统域。
  - **第二部分：能力演进矩阵与子文档路由（结构化表格）**：
    - 梳理不同版本或改造前后的能力对比，清晰标注支持状态（`✅ / 🚧 / ⏳ / ⚠️ / ❌`）并进行差异说明；
    - 承担路由中心职责：在表格最后一列直接挂接深度子文档相对路径（`[[子文档相对路径]]`）或同页小节锚点（`[[#技术实现细节]]`）。
  - **第三部分：技术规格与实现细节（深度文本正文）**：
    - 详细描述协议契约、DDL 变更、算法伪代码、并发控制、容灾降级与未验证项；专供深度技术评审与 AI Agent 精确读取上下文。
- **模板匹配规则**：
  - 业务方案与改造任务从 `_templates/initiative-readme.md` 派生；
  - 系统架构与设计从 `_templates/architecture.md` 派生；
  - 核心功能模块从 `_templates/module.md` 派生；
  - 原始输入快照与会议纪要从 `_templates/raw-snapshot.md` 派生；
  - 通用长期技术页面从 `_templates/wiki.md` 派生；
  - 架构范围导航页从 `_templates/architecture-scope-readme.md` 派生，保持轻量、只做本地索引；
  - 架构决策直接内嵌在方案与架构中，不再维护独立的 ADR 模板；代码仓库说明以代码仓自带 README 为准，不再维护 `repo-readme.md`。
- **绿色证据必须注明实际范围**：代码已实现不等于已合入，合入不等于已部署，部署不等于验收通过；raw 快照中“材料已记录 / 已达成共识”也不代表主张已经过代码或运行时核实。引用未合入实现时同时注明分支、完整 commit、路径行号与验证范围。

## 索引与审计

- 每个新长期页面和专项 `README.md` 进入 `_index/topic-map.md`。
- 新架构页同时进入所属 scope 的 `README.md`，并位于 topic map 的对应 scope 分组。
- 专项子页面只进入专项 README 的本地索引。
- 新 raw 快照进入 `raw/_manifest.md`。
- 写入审计由 Git commit/MR 承担，不创建或提交逐次操作日志；`$query` 和 `$lint` 严格只读。

## 变更与发布边界

- 普通知识写入与知识库治理变更分开路由，基线准备和执行模式详见 `workflows/knowledge-base-change-policy.md`。
- 修改型任务开始前，应在干净 checkout 中同步采用仓库配置的目标分支；未配置时使用仓库默认分支。`$query`、`$lint` 以及不修改仓库的分析、研究或计划任务保持只读，不切分支或拉取代码。
- 只有用户或上层任务明确要求执行已批准的实施计划时，才进入“实现 → 最小相关测试 → 修复 → 回归验证”循环；普通知识库 Skill 不自动进入该模式。
- Agent 规则、Skill、验证脚本、发布自动化以及批量移动或删除属于**跨边界治理**，会改变本仓之外的行为，默认需要独立审查。目录调整、模板、Schema、Mermaid 配色和索引重组只改变本仓内容，属**仓内治理**，与普通知识同路由。判定不确定时按跨边界治理处理。
- 本模板不假设默认分支、直推权限、代码托管平台或自动发布器；提交、推送、创建评审或发布前必须依据当前仓库的显式规则和授权。

## 安全与质量

- 不写入 token、密码、密钥、连接串、个人敏感信息或未获授权的受限原文。
- 外部来源记录来源标识、获取日期和权限边界。
- 修改前检查已有未提交变更，不覆盖或整理无关内容。
- 修改后检查 frontmatter、链接、索引、manifest 和敏感信息；如位于 Git 仓库，运行 `git diff --check` 和 `git status --short`。
- 涉及架构页时，额外运行 `.agents/skills/lint/scripts/check-architecture-layout.sh`。

## 可用 Skills

- `$query`：只读查询。
- `$lint`：只读健康检查。
- `$add-wiki`：创建或更新页面。
- `$digest`：消化已解决的经验。
- `$ingest`：归档并编译原始资料。
